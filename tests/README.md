# tests — 퍼즈 테스트 하니스

계산기와 워커를 **무작위 입력으로 두들겨보는** 테스트. 배포 대상이 아니다
(Pages에 파일은 올라가지만 실행되지 않는다).

| 파일 | 대상 | 실행 |
|---|---|---|
| `fuzz-personas.js` | 계산기 (`../index.html`) | 브라우저 콘솔 |
| `fuzz-worker.mjs` | 워커 (`../worker/index.js`) — `/?url=` + `/rate` | Node |
| `negcontrol-parse.js` | 오퍼 파서 **음성 대조군** (개발용) | 브라우저 콘솔 |
| `negcontrol-worker.mjs` | 워커 **음성 대조군** (개발용) | Node |
| `negcontrol-scan.js` | 바코드 스캐너 **음성 대조군** (개발용) | 브라우저 콘솔 |
| `scan-field-test.html` | 바코드 **실기 인식률 측정** (개발용·폰에서) | 폰 브라우저 |

## 계산기 하니스

로컬 서버로 계산기를 열고 콘솔에서:

```bash
python -m http.server 8899
```

```js
fetch('site/tests/fuzz-personas.js').then(r=>r.text()).then(eval)
__fuzz.all({seed:42})        // 전부
__fuzz.runGolden()           // 손계산 정답 10개
__fuzz.run({n:2000,seed:42}) // 수학 퍼즈
__fuzz.runDom({n:60,seed:7}) // 실제 UI 렌더
__fuzz.runCompare({n:200})   // 비교표·결론 정합성
__fuzz.runParse()            // v0.28 오퍼 붙여넣기 파서 (골든 159개)
__fuzz.runScan().then(console.log)  // v0.29 바코드 스캐너 (골든 53개) — 유일하게 async
```

랜덤 페르소나 = 지갑 카드 조합 · 포인트 가치관 · 카테고리 · 판매처(오타·미등록 포함)
· 가격(경계값 포함) · 세금 · 배송 · 쿠폰 · 포털% · 오퍼. 시드 PRNG라 실패는 재현된다.

## 워커 하니스

```bash
node site/tests/fuzz-worker.mjs site/worker/index.js 42        # 658 + /rate 89
node site/tests/negcontrol-worker.mjs site/worker/index.js 42  # 음성 대조군 (변형 12종)
```

`fetch`·`caches`·`ctx`를 스텁으로 갈아끼워 **실제 소매 사이트·포털로는 요청이 나가지 않는다.**
결과와 남은 과제는 `../worker/README.md` 의 "퍼즈 테스트 결과" 절에 있다.

`negcontrol-worker.mjs` 는 워커 소스에 변형을 하나씩 먹인 사본으로 하니스를 돌려
**그 검사가 실제로 실패하는지** 센다. `negcontrol-parse.js` 와 마찬가지로 `소스변경` 필드를
같이 찍는다 — **이 값이 `false` 인데 실패가 0이면 통과가 아니라 변형이 안 먹은 것이다.**
⚠️ `worker/index.js` 는 CRLF라 변형 `from` 문자열은 **한 줄로** 써야 매치된다.

## 규칙: 통과했다는 말은 음성 대조군을 거친 뒤에만 유효하다

**검사를 추가하면 대상 코드를 일부러 망가뜨려서 그 검사가 실패하는지 확인할 것.**
확인 없이 "0건 실패"는 아무 의미가 없다. 실제로 두 하니스 모두 이 절차에서
자기 허점이 드러났다.

계산기 하니스 자기감사(2026-08-12)에서 **6종이 조용히 통과**했다:

| 망가뜨린 것 | 감사 전 | 지금 |
|---|---|---|
| 적립 배수를 전부 1로 | 0건 | 175건 |
| 포인트 가치를 전부 5¢로 | 0건 | 197건 |
| 포털 캐시백 통째로 무시 | 0건 | 292건 |
| 오퍼 통째로 무시 | 0건 | 161건 |
| 결론 렌더를 빈칸으로 | 0건 | 20건 |
| `[object Object]` / `${...}` 누출 | 0건 | 21건 |

원인은 하나다. **항등식·정렬·단조성은 내부 일관성만 본다.** 값이 전부 틀려도 서로
앞뒤가 맞으면 통과하고, 기능이 죽어도 "나빠지지는 않았으니" 통과하고, 아무것도
안 그려도 오염될 문자가 없으니 통과한다. 그래서 지금은 **골든 케이스(손계산 정답)**,
**카탈로그 교차검증**, **"정확히 이만큼 변해야 함"**(포털 1%p = 소계의 1%,
오퍼 $10 = 현금 +$10), **렌더 실질 검사**가 함께 들어가 있다.

워커 하니스에서도 같은 절차로 두 가지가 나왔다 — SSRF 합격선이 느슨했던 것(나간 곳을
다시 판정하다 정규화된 형태를 놓쳤다 → `egress === 0` 으로 교체), 그리고 `fetch` 스텁이
`redirect` 옵션을 무시해서 리다이렉트 검사가 아무것도 보증하지 못했던 것.

**세 번째 사례(v0.27):** 비교표가 접힌 `<details>`(`#whyPanel`) 안으로 들어가자
`innerText` 가 빈 문자열을 돌려주기 시작했고, 비교표 대상 검사가 조용히 헛돌았다
→ `textContent` 로 교체. **UI 구조가 바뀌면 하니스가 침묵하는 방식으로 깨진다** —
그래서 "아무것도 렌더되지 않음"을 명시적으로 실패로 잡는 검사가 반드시 필요하다.
숨김·접힘 요소를 읽을 때는 `innerText` 대신 `textContent` 를 쓸 것.

**네 번째 사례(트랙 C UI 개편, 2026-08-12):** 카드 상세표(`#cardbody`, 섹션
«다른 카드로 사면?»)에는 `DIRT` 정규식만 걸려 있었고 `checkRendered` 가 없었다.
표를 **통째로 비워도, 카드로 감싸 접어도 0건**이었다 — 빈 문자열엔 오염이 없으니까.
`runDom` 에 `checkRendered` + **행 수 = 지갑 카드 수** 검사를 추가했다.

| 망가뜨린 것 | 감사 전 | 지금 |
|---|---|---|
| `#cardbody` 통째로 비움 | 0건 | 22건 |
| 카드표 행 1개 삭제 | 0건 | 22건 |

(22 = 25회 중 지갑이 비지 않은 횟수. 지갑이 비면 `recompute` 가 이 카드를 숨기므로
검사도 같이 건너뛴다.)

**예외 한 곳 — `#finalConclusion` 은 일부러 `innerText` 로 읽는다.** 결론은 이 도구의
답이고 *클릭 없이 보여야 한다*는 제품 불변식이라, 누가 접거나 숨기면 곧바로 시끄럽게
실패하는 게 맞다(접힘 대조군 25/25 확인). `textContent` 로 "통일"하면 이 감시가 사라진다.

**다섯 번째 사례 — 반대 방향의 사고: 하니스가 낡아서 정상 동작을 실패로 보고했다.**
쿠폰 ≥ 정가 버그를 고치면서 `recompute()` 의 순위 필터가 `r.price > 0` → `r.hasInput` 로
바뀌었는데, `runCompare` 의 '정답' 계산은 `r.price > 0` 으로 남아 있었다. 그 결과
**청구액 $0 인 판매처를 1위로 올리는 (이제는 올바른) 동작이 seed 2026 에서 6건의 실패로
보고됐다.** 위 "넘길 것" 절에 *"필터를 바꾸면 그 검사도 같이 맞춰야 한다"* 고 적어둔
바로 그 지점이었다 — 적어놨는데도 놓쳤다.

교훈: **하니스가 제품 로직을 복제하는 곳은 전부 시한폭탄이다.** 여기서는 필터 한 줄이
두 곳에 있었다. 실패가 뜨면 "제품이 틀렸나"만이 아니라 **"하니스가 낡았나"** 도 같이 의심할 것.
고친 뒤에는 반드시 대조군으로 *검사가 아직 살아있는지* 확인해야 한다(실패를 없애는
가장 쉬운 방법은 검사를 죽이는 것이므로). 이번 확인:

| 망가뜨린 것 | 결과 |
|---|---|
| 비교표 순위 역전 | 100/100 |
| 결론 배지에서 판매처명 제거 | 100/100 |
| 비교표 통째로 비움 | 100/100 |
| 대조군(정상) | 0 |

⚠️ **하니스를 고친 뒤 대조군을 돌릴 땐 캐시버스터를 붙일 것** —
`fetch('site/tests/fuzz-personas.js?cb='+Date.now())`. 안 붙이면 브라우저가 옛 파일을
돌려주고, 방금 추가한 검사가 "여전히 0건"으로 보여 **고치기 전과 구분이 안 된다.**
이번에도 실제로 한 번 속았다.

**여섯 번째 사례 — v0.28 오퍼 붙여넣기 파서(`runParse`).** 이 파서는 **개수를 세는 검사로는
못 잡는 방식으로 틀린다.** 가맹점명 줄을 한 칸 잘못 집어도 오퍼 개수는 그대로고, 결과는
*"엉뚱한 가게의 오퍼가 이 가게에 붙는 것"* — 순위를 조용히 뒤집는, 이 도구 최악의 실패 모드다.
그래서 `runParse` 는 개수가 아니라 **가맹점명·종류·금액·%·상한·최소사용액·만료일을 행 단위로
못 박는다**(익명 픽스처 2종에 골든 159개).

픽스처는 **익명 샘플**이다 — 실제 사용자 덤프(`evidence/`)는 개인 오퍼라 이 repo에 넣지 않고,
관찰된 **구조만** 옮겼다. 픽스처 설계 도중 실제로 결함 2개가 드러났다:
`45d left`(만료 잔여물)가 **다음 오퍼의 가맹점명으로 잡히는 것**, 그리고 뒤따르는 `New` 뱃지가
사실은 **다음 블록의 시작**이라 엉뚱한 오퍼에 붙던 것.

음성 대조군은 `negcontrol-parse.js` 로 자동화했다. 페이지의 파서 구간을 떼어내 변형을 먹인 뒤
`new Function` 으로 다시 만들어 `window` 에 갈아끼우고 `runParse` 를 돌린다(끝나면 원복).

```js
fetch('tests/fuzz-personas.js?cb='+Date.now()).then(r=>r.text()).then(eval)
fetch('tests/negcontrol-parse.js?cb='+Date.now()).then(r=>r.text()).then(eval)
__negParse().then(o=>console.table(o))
```

| 망가뜨린 것 | 실패 |
|---|---|
| 설명문 판정을 꺼버림 (가맹점명 자리에 홍보문구) | 6 |
| 값 줄 하드스톱 제거 (앞 오퍼의 `15% cash back` 이 가맹점명이 됨) | 4 |
| `Nd left` 건너뛰기 제거 (만료 잔여물이 가맹점명이 됨) | 3 |
| 중복 제거를 끔 (캐러셀 오퍼를 두 번 셈) | 16 |
| **Chase 만료일을 지어냄** (소스에 없는 값을 만들어냄) | 8 |
| **못 읽은 블록을 조용히 버림** | 2 |
| 가맹점 대조를 부분일치로 완화 (엉뚱한 가게 오퍼가 붙음) | 1 |
| 마일 오퍼를 현금으로 취급 | 4 |
| 만료된 오퍼를 계속 제안 | 1 |
| 최소 사용액 미달을 무시 | 1 |
| 퍼센트 오퍼 상한을 무시 | 1 |
| **가맹점명 대신 혜택 문구를 저장** (개수는 그대로 — 개수만 세면 못 잡는다) | 7 |
| 대조군(정상) | **0** |

⚠️ **`ofpValue` / `ofpIsDescription` / `ofpStoreHit` / `ofpAmountFor` / `parseOfferDump` 는
이름으로 찾는다.** 개명하면 `negcontrol-parse.js` 의 변형 문자열도 같이 고쳐야 하고, 안 고치면
**변형이 안 먹은 채로 "대조군이 통과했다"고 보고한다** — 그래서 `소스변경` 필드를 같이 찍는다.
이 값이 `false` 인데 실패가 0이면 그건 통과가 아니라 **검사가 헛돈 것**이다.

**일곱 번째 사례 — v0.29 `/rate` 온디맨드 요율 조회.** 이 엔드포인트의 최악의 실패 모드는
SSRF가 아니라 **"못 찾음"을 "0%"로 뭉개는 것**이다. 응답 형태가 같아서 개수·형식 검사로는
안 잡히고, 결과는 *조회에 실패한 판매처를 캐시백 0%로 깎아 순위에서 밀어내는 것* —
계산기가 조용히 틀린 답을 낸다. 그래서 골든 19케이스가 `pct`·`listed`·`status`·`upTo`·`flat`
을 행 단위로 못 박고, 봇 차단은 **실패 사유 문구**까지 본다(상태만 보면 "못 읽음"과 같다).

프라이버시 조건 두 개도 하니스가 실행으로 확인한다 — `/rate` 처리 중 `console.*` 호출
0건(조건 1), 오리진이 달라도 같은 매장이면 캐시 히트(조건 3). 약속을 문서가 아니라
**깨면 실패하는 검사**로 걸어둔 것이다. 변형 12종 전부 걸리고 대조군은 0 —
표는 `../worker/README.md`.

여기서도 **하니스가 정상 동작을 실패로 보고하는** 다섯 번째 사례가 반복됐다: 적대적 슬러그
목록의 `nike`/`NIKE`/`' nike '` 가 같은 슬러그로 정규화되면서 두 번째부터 캐시 히트가 났고,
"포털 2곳으로 안 나갔다"는 실패 3건이 떴다. 실제로는 **정규화가 일관됐다는 증거**였다.
실패가 뜨면 "제품이 틀렸나"와 **"하니스가 틀렸나"** 를 같이 의심할 것.

**여덟 번째 사례 — v0.29 매장 바코드 스캔(`runScan`).** 이 기능의 최악의 실패 모드는
"못 읽음"이 아니라 **그럴듯한 12자리를 만들어내는 것**이다. 그러면 개수는 똑같이 1이고
형식도 멀쩡한데 사용자는 **엉뚱한 상품 페이지**를 보게 된다 — 개수·형식 검사로는 절대 안 잡힌다.
그래서 `runScan` 은 체크디지트·정규화·UPC-E 복원·손입력 거절 사유·딥링크·재시도 판정을
**전부 값 단위로 못 박는다**(골든 53개).

골든의 출처가 중요하다. UPC 10개는 **우리가 만든 숫자가 아니라 조사 문서가 실제로 조회에 쓴 것**이고
(`리서치/바코드-매장스캔-조사.md` 3-B·3-E·9-A·9-B), UPC-E 기대값 4개는 **명세에서 손으로 편 것**이다
(`expandUpcE` 로 만들면 동어반복이 된다 — 다섯 번째 사례의 교훈).

`runScan` 은 이 하니스에서 **유일하게 async** 다(`decodeWithRetries` 가 비동기라서).
그래서 `__fuzz.all()` 에 넣지 않았다 — 넣으면 기존 기준선 명령이 통째로 async 가 된다.
**따로 돌리고 따로 보고할 것.**

음성 대조군은 `negcontrol-scan.js`. `scanner.js` 는 ES 모듈이라 `negcontrol-parse.js` 와 방식이 조금
다르다: `import.meta` 와 `export` 를 걷어내고 `new Function` 으로 다시 만든 뒤 그 객체를
**`runScan(mod)` 에 인자로 넘긴다**(전역 `window.__scanner` 는 안 건드린다).

```js
fetch('tests/fuzz-personas.js?cb='+Date.now()).then(r=>r.text()).then(eval)
fetch('tests/negcontrol-scan.js?cb='+Date.now()).then(r=>r.text()).then(eval)
__negScan().then(o=>console.table(o))
```

| 망가뜨린 것 | 실패 |
|---|---|
| 체크디지트 검사를 꺼버림 (오타 난 번호를 그대로 검색) | 13 |
| 체크디지트 가중치를 뒤집음 (3,1 → 1,3) | 23 |

## ✅ 해결됨 — 쿠폰이 정가보다 크면 그 판매처가 결론에서 사라진다

**상태: 2026-08-12 수정 완료(트랙 A).** 아래는 발견 당시 기록이고, 처분은 이 절 끝에 있다.

`recompute()` 는 `results.filter(r => r.price > 0)` 으로 순위를 매긴다. 여기서 `r.price` 는
정가가 아니라 **청구액**(`소계 + 세금 + 배송`)이고, 소계는 `max(0, 정가 − 쿠폰)` 이다.
그래서 **쿠폰 ≥ 정가 이고 세금·배송이 없으면 청구액이 $0 이 되어 그 판매처가 비교
대상에서 통째로 빠진다.** (소계가 0이면 세금도 0이므로 세금률을 올려도 살아나지 않는다.)

재현 (지갑에 Active Cash 1장, 카테고리 온라인):

| # | 시나리오 | 화면 결과 |
|---|---|---|
| A | Nike 정가 $50 · 쿠폰 $60 (유일) | 비교표 0행 · 결론이 **"판매처에 가격을 넣으면 비교가 시작돼."** — 가격을 넣었는데 넣으라고 한다 |
| B | 위 + Target $45 + Amazon $48 | Nike가 표에서 **사라지고 Target $45 를 1위로 추천** |
| C | 위 A + 배송비 $5 | 정상 — Nike가 `$5.00` 으로 1위 |
| D | A + 판매세 8% | 여전히 0행 (소계 0 → 세금 0) |

**B가 문제의 핵심이다.** $0 에 살 수 있는 선택지를 빼놓고 $45 를 쓰라고 추천한다.
순비용 최소화라는 이 도구의 존재 이유와 정면으로 어긋난다. A는 그보다 덜 위험하지만
(잘못된 추천이 아니라 무응답), 사용자가 입력을 의심하게 만든다.

빈도는 낮다 — 쿠폰이 상품값을 넘는 경우이므로 기프트카드·크레딧·100% 오프 프로모
정도다. 하지만 **틀리는 방향이 나쁘다**(공짜를 버리고 유료를 고른다).

고칠 때 생각할 것:

- 필터 기준을 청구액 `> 0` 에서 **"가격 입력이 있었는가"**(`정가 > 0` 또는 쿠폰·배송 중
  하나라도 입력됨)로 바꾸면 A·B 둘 다 해결된다. 청구액 $0 행은 `$0.00` 으로 표시하고
  1위로 올리면 된다.
- 다만 **쿠폰이 정가를 넘는 만큼은 돌려주지 않는다**($60 쿠폰을 $50 상품에 쓰면 $10 은
  버려진다). 지금 `Math.max(0, 정가 − 쿠폰)` 은 이 부분을 이미 맞게 처리하고 있으니,
  표시만 `$0.00` 으로 하고 "쿠폰 $10 남음(대개 소멸)" 같은 안내를 붙이는 게 정직하다.
- 포털 캐시백은 소계(=0) 기준이라 자동으로 $0 이 된다 — 실제로도 $0 결제엔 캐시백이
  안 붙으므로 맞다.
- 하니스 쪽은 이미 이 기준을 알고 있다 (`runDom` 의 비교표 행 수 검사가 **청구액**
  기준으로 세도록 고쳐져 있다). 필터를 바꾸면 그 검사도 같이 맞춰야 한다.

발견 경로: 렌더 실질 검사를 새로 넣었을 때 정상 상태에서 1건이 걸렸다. 원인을 파보니
하니스 기준이 틀린 것(정가로 셌다)이었지만, 그 과정에서 이 제품 동작이 드러났다.

### 처분 (2026-08-12, 트랙 A)

권고안대로 **필터 기준을 청구액에서 "가격을 입력했는가"로 바꿨다** — `scenarioResult` 가
`hasInput`(정가>0 또는 배송비>0)과 `couponLeft`(못 쓰고 남는 쿠폰)를 함께 내주고,
`recompute()` 의 순위 필터가 `r.hasInput` 을 쓴다. 시나리오 A·B 둘 다 해소:

| # | 화면 결과 (수정 후) |
|---|---|
| A | Nike 1행 · 카드 칸 `결제액 $0 — 카드 무관` · 영수증에 `쿠폰 $10.00는 남아서 못 씀 — 대개 소멸` |
| B | **Nike $0.00 이 1위**, Target $43.20 이 2위 |

영수증의 쿠폰 줄은 정가까지만 차감해 표시하고(`min(쿠폰, 정가)`), $0 결제에선 카드 줄을
아예 숨긴다(`−$0.00` 은 정보가 아니다).

⚠️ **하니스 쪽에서 배운 것:** 행 수 검사의 기대값을 처음엔 앱의 `hasInput` 을 읽어서
만들었는데, 그러면 **앱이 틀려도 같이 틀리는 동어반복**이 된다(음성 대조군이 통과해버린다).
지금은 하니스가 `(정가>0 || 배송비>0)` 을 **독립적으로** 다시 센다. 음성 대조군 결과:
`hasInput` 을 옛 기준(`price>0`)으로 되돌리면 `비교표 행 수 1 ≠ 가격 있는 판매처 2` 로
2건 실패, 되돌리면 0건.
