# tests — 퍼즈 테스트 하니스

계산기와 워커를 **무작위 입력으로 두들겨보는** 테스트. 배포 대상이 아니다
(Pages에 파일은 올라가지만 실행되지 않는다).

| 파일 | 대상 | 실행 |
|---|---|---|
| `fuzz-personas.js` | 계산기 (`../index.html`) | 브라우저 콘솔 |
| `fuzz-worker.mjs` | 가격조회 워커 (`../worker/index.js`) | Node |

## 계산기 하니스

로컬 서버로 계산기를 열고 콘솔에서:

```bash
python -m http.server 8899
```

```js
fetch('site/tests/fuzz-personas.js').then(r=>r.text()).then(eval)
__fuzz.all({seed:42})        // 전부
__fuzz.runGolden()           // 손계산 정답 10개
__fuzz.run({n:2000,seed:42}) // 수학 퍼즈
__fuzz.runDom({n:60,seed:7}) // 실제 UI 렌더
__fuzz.runCompare({n:200})   // 비교표·결론 정합성
```

랜덤 페르소나 = 지갑 카드 조합 · 포인트 가치관 · 카테고리 · 판매처(오타·미등록 포함)
· 가격(경계값 포함) · 세금 · 배송 · 쿠폰 · 포털% · 오퍼. 시드 PRNG라 실패는 재현된다.

## 워커 하니스

```bash
node site/tests/fuzz-worker.mjs site/worker/index.js 42
```

`fetch`·`caches`·`ctx`를 스텁으로 갈아끼워 **실제 소매 사이트로는 요청이 나가지 않는다.**
결과와 남은 과제는 `../worker/README.md` 의 "퍼즈 테스트 결과" 절에 있다.

## 규칙: 통과했다는 말은 음성 대조군을 거친 뒤에만 유효하다

**검사를 추가하면 대상 코드를 일부러 망가뜨려서 그 검사가 실패하는지 확인할 것.**
확인 없이 "0건 실패"는 아무 의미가 없다. 실제로 두 하니스 모두 이 절차에서
자기 허점이 드러났다.

계산기 하니스 자기감사(2026-08-12)에서 **6종이 조용히 통과**했다:

| 망가뜨린 것 | 감사 전 | 지금 |
|---|---|---|
| 적립 배수를 전부 1로 | 0건 | 175건 |
| 포인트 가치를 전부 5¢로 | 0건 | 197건 |
| 포털 캐시백 통째로 무시 | 0건 | 292건 |
| 오퍼 통째로 무시 | 0건 | 161건 |
| 결론 렌더를 빈칸으로 | 0건 | 20건 |
| `[object Object]` / `${...}` 누출 | 0건 | 21건 |

원인은 하나다. **항등식·정렬·단조성은 내부 일관성만 본다.** 값이 전부 틀려도 서로
앞뒤가 맞으면 통과하고, 기능이 죽어도 "나빠지지는 않았으니" 통과하고, 아무것도
안 그려도 오염될 문자가 없으니 통과한다. 그래서 지금은 **골든 케이스(손계산 정답)**,
**카탈로그 교차검증**, **"정확히 이만큼 변해야 함"**(포털 1%p = 소계의 1%,
오퍼 $10 = 현금 +$10), **렌더 실질 검사**가 함께 들어가 있다.

워커 하니스에서도 같은 절차로 두 가지가 나왔다 — SSRF 합격선이 느슨했던 것(나간 곳을
다시 판정하다 정규화된 형태를 놓쳤다 → `egress === 0` 으로 교체), 그리고 `fetch` 스텁이
`redirect` 옵션을 무시해서 리다이렉트 검사가 아무것도 보증하지 못했던 것.

**세 번째 사례(v0.27):** 비교표가 접힌 `<details>`(`#whyPanel`) 안으로 들어가자
`innerText` 가 빈 문자열을 돌려주기 시작했고, 비교표 대상 검사가 조용히 헛돌았다
→ `textContent` 로 교체. **UI 구조가 바뀌면 하니스가 침묵하는 방식으로 깨진다** —
그래서 "아무것도 렌더되지 않음"을 명시적으로 실패로 잡는 검사가 반드시 필요하다.
숨김·접힘 요소를 읽을 때는 `innerText` 대신 `textContent` 를 쓸 것.

## 넘길 것 — 쿠폰이 정가보다 크면 그 판매처가 결론에서 사라진다

**상태: 미수정. 제품 판단이 필요해서 손대지 않았다.**

`recompute()` 는 `results.filter(r => r.price > 0)` 으로 순위를 매긴다. 여기서 `r.price` 는
정가가 아니라 **청구액**(`소계 + 세금 + 배송`)이고, 소계는 `max(0, 정가 − 쿠폰)` 이다.
그래서 **쿠폰 ≥ 정가 이고 세금·배송이 없으면 청구액이 $0 이 되어 그 판매처가 비교
대상에서 통째로 빠진다.** (소계가 0이면 세금도 0이므로 세금률을 올려도 살아나지 않는다.)

재현 (지갑에 Active Cash 1장, 카테고리 온라인):

| # | 시나리오 | 화면 결과 |
|---|---|---|
| A | Nike 정가 $50 · 쿠폰 $60 (유일) | 비교표 0행 · 결론이 **"판매처에 가격을 넣으면 비교가 시작돼."** — 가격을 넣었는데 넣으라고 한다 |
| B | 위 + Target $45 + Amazon $48 | Nike가 표에서 **사라지고 Target $45 를 1위로 추천** |
| C | 위 A + 배송비 $5 | 정상 — Nike가 `$5.00` 으로 1위 |
| D | A + 판매세 8% | 여전히 0행 (소계 0 → 세금 0) |

**B가 문제의 핵심이다.** $0 에 살 수 있는 선택지를 빼놓고 $45 를 쓰라고 추천한다.
순비용 최소화라는 이 도구의 존재 이유와 정면으로 어긋난다. A는 그보다 덜 위험하지만
(잘못된 추천이 아니라 무응답), 사용자가 입력을 의심하게 만든다.

빈도는 낮다 — 쿠폰이 상품값을 넘는 경우이므로 기프트카드·크레딧·100% 오프 프로모
정도다. 하지만 **틀리는 방향이 나쁘다**(공짜를 버리고 유료를 고른다).

고칠 때 생각할 것:

- 필터 기준을 청구액 `> 0` 에서 **"가격 입력이 있었는가"**(`정가 > 0` 또는 쿠폰·배송 중
  하나라도 입력됨)로 바꾸면 A·B 둘 다 해결된다. 청구액 $0 행은 `$0.00` 으로 표시하고
  1위로 올리면 된다.
- 다만 **쿠폰이 정가를 넘는 만큼은 돌려주지 않는다**($60 쿠폰을 $50 상품에 쓰면 $10 은
  버려진다). 지금 `Math.max(0, 정가 − 쿠폰)` 은 이 부분을 이미 맞게 처리하고 있으니,
  표시만 `$0.00` 으로 하고 "쿠폰 $10 남음(대개 소멸)" 같은 안내를 붙이는 게 정직하다.
- 포털 캐시백은 소계(=0) 기준이라 자동으로 $0 이 된다 — 실제로도 $0 결제엔 캐시백이
  안 붙으므로 맞다.
- 하니스 쪽은 이미 이 기준을 알고 있다 (`runDom` 의 비교표 행 수 검사가 **청구액**
  기준으로 세도록 고쳐져 있다). 필터를 바꾸면 그 검사도 같이 맞춰야 한다.

발견 경로: 렌더 실질 검사를 새로 넣었을 때 정상 상태에서 1건이 걸렸다. 원인을 파보니
하니스 기준이 틀린 것(정가로 셌다)이었지만, 그 과정에서 이 제품 동작이 드러났다.
