# probe-data — P3 요율 변동 측정 데이터 전용 브랜치

**여기엔 사이트 코드가 없다.** `rate-probe.jsonl` 하나뿐이다.

## 왜 별도 브랜치인가

`main` 은 GitHub Pages 소스 브랜치다(`build_type: legacy`, `source.branch: main`).
**main 커밋 하나 = 배포 하나**다. 측정 워크플로가 매시간 커밋하면 **하루 24회 배포**가
일어난다. 실제로 그랬다 — 8/25 13:01Z·14:00Z 봇 커밋이 각각 Pages 배포를 일으켰다.

측정 데이터는 **라이브 사이트가 읽지 않는다.** main 에 있을 이유가 없었다.
Pages 는 소스 브랜치에만 반응하므로 이 브랜치에 쌓으면 배포가 0이 된다.

## 이 브랜치의 이력

- **부모 없는(orphan) 커밋**으로 시작한다. 사이트 이력을 끌고 오지 않는다.
- 첫 커밋의 `rate-probe.jsonl` 은 **main 에 쌓여 있던 초기 회차를 그대로 복사**한 것이다.
  회차가 끊기지 않게 하려는 것이다.
- ⚠️ **진짜 데이터는 이 브랜치다.** `main` 에도 같은 이름의 사본이 남아 있는데
  그건 8/25 전환 이전의 잔재이고, **다음에 정당한 배포를 할 때 삭제한다.**
  (지우려고 main 에 커밋하면 그것도 배포라서 지금은 안 지운다.)

## 읽는 법

한 줄 = 한 판매처의 한 회차.

```
{"t":"<UTC ISO>","store":"nike","rk":4,"tcb":6}
```

- `rk` = Rakuten · `tcb` = TopCashback (기본 캐시백 %)
- `rkUpTo`/`tcbUpTo` = 그 값이 "최대 N%" 라는 뜻 (확정치가 아니다)
- `rkFlat` = % 가 아니라 $ 고정 (Amazon 류)
- `rkFail`/`tcbFail` = **못 읽었다.** ⚠️ 값은 `null` 이고 **0 이 아니다** —
  0 으로 적으면 나중에 "그 시각에 0으로 떨어졌다"는 **없는 변동**을 만들어낸다
- 그 회차에 아예 줄이 없는 판매처 = 연속 실패로 **건너뛴** 것 (차단 회피)

## 종료

`scripts/probe-rates.mjs` 가 시작일 +5일이 지나면 스스로 아무것도 안 하고 끝난다.
워크플로를 지우는 걸 누가 잊어도 요청이 계속 나가지 않는다.

## 중간 관측 (2026-08-25 12:57Z ~ 23:34Z · 13회차)

### 요율 변동 — 사실상 없다

8곳 중 7곳이 11시간 동안 **완전히 고정**이었다.

```
booking ≤8%/0%   expedia ≤3%/≤10%   gnc 2%/8%    macys 4%/≤7%
nike    4%/6%    logitech 3%/4%     athleta 2%/4%
```

**adidas 하나만 움직였고, 그것도 애매하다:**

```
12:57Z ~ 21:39Z   rk ≤4% (upTo)        ← 11회차 고정
22:41Z            rk  4% (upTo 사라짐, 숫자는 그대로)
23:34Z            rk  FAIL
```

⚠️ **"요율이 바뀌었다"로 읽지 말 것.** 바뀐 건 숫자가 아니라 **"최대"라는 말**이다
(Rakuten 타이틀에서 `Up to` 가 빠졌다). 두 가지로 읽힌다:

- **진짜 변경** — "최대 4%" → "4% 확정". 그렇다면 의미 있다(≤4% 와 4% 는 사용자에게 다른 값)
- **페이지 쪽 사정** — 타이틀 형식이 바뀌었거나 다른 변형이 나왔다

**이 데이터로는 둘을 구분할 수 없다.** 그리고 **바로 다음 회차에 그 판매처만 FAIL** 했다 —
값이 바뀐 게 아니라 adidas 페이지에 뭔가 일어나는 중일 가능성이 더 커 보인다.
한 판매처 · 연속 두 회차 · 관측 구간 끝이라 **판정을 미룬다.**

### 차단 징후 — 없다

실패 1건 / 104줄 · 건너뜀 0회 · 13회차 전부 8줄씩 온전 · 응답 형태 변화 없음.

### ⚠️ cron 의 분(minute)은 지켜지지 않는다

`cron: '7 * * * *'` 인데 실제 실행 시각:

```
14:00 · 15:00 · 15:55 · 16:51 · 17:42 · 18:54 · 19:42 · 20:42 · 21:39 · 22:41 · 23:34
간격:   60 · 56 · 56 · 50 · 72 · 48 · 60 · 57 · 62 · 53분
```

**분은 아무 의미가 없고** 간격도 48~72분으로 흔들린다. 시간당 1회는 지켜지므로
측정에는 지장이 없다.

⚠️ **`update-rates.yml` 의 `:17` 도 같은 처지다.** 그 값은 *"정각 혼잡 회피"* 를 근거로
골랐는데 **그 근거가 성립하지 않는다.** 지금 판단에 영향은 없다(P3 가 재는 건
*포털이 언제 바꾸나*지 *우리가 언제 재나*가 아니다). 나중에 갱신 지연이 문제 되면
여기서 시작할 것.

### 잠정 판단 (결론 아님)

11시간 · 8곳에서 변동이 사실상 0이다. 이게 유지되면 *"update-rates 를 몇 시에 돌리나"* 는
**애초에 별로 중요하지 않은 질문**이었다는 뜻이 된다.

⚠️ **다만 11시간은 하루도 안 된다.** 대상 선정 근거였던 변동률(.36~.88)은 **일 단위**다.
하루 한 번 바뀌는 값이면 지금 창에 안 걸리는 게 정상이다. 창은 8/30 까지다.
