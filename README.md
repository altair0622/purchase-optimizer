# probe-data — P3 요율 변동 측정 데이터 전용 브랜치

**여기엔 사이트 코드가 없다.** `rate-probe.jsonl` 하나뿐이다.

## 왜 별도 브랜치인가

`main` 은 GitHub Pages 소스 브랜치다(`build_type: legacy`, `source.branch: main`).
**main 커밋 하나 = 배포 하나**다. 측정 워크플로가 매시간 커밋하면 **하루 24회 배포**가
일어난다. 실제로 그랬다 — 8/25 13:01Z·14:00Z 봇 커밋이 각각 Pages 배포를 일으켰다.

측정 데이터는 **라이브 사이트가 읽지 않는다.** main 에 있을 이유가 없었다.
Pages 는 소스 브랜치에만 반응하므로 이 브랜치에 쌓으면 배포가 0이 된다.

## 이 브랜치의 이력

- **부모 없는(orphan) 커밋**으로 시작한다. 사이트 이력을 끌고 오지 않는다.
- 첫 커밋의 `rate-probe.jsonl` 은 **main 에 쌓여 있던 초기 회차를 그대로 복사**한 것이다.
  회차가 끊기지 않게 하려는 것이다.
- ⚠️ **진짜 데이터는 이 브랜치다.** `main` 에도 같은 이름의 사본이 남아 있는데
  그건 8/25 전환 이전의 잔재이고, **다음에 정당한 배포를 할 때 삭제한다.**
  (지우려고 main 에 커밋하면 그것도 배포라서 지금은 안 지운다.)

## 읽는 법

한 줄 = 한 판매처의 한 회차.

```
{"t":"<UTC ISO>","store":"nike","rk":4,"tcb":6}
```

- `rk` = Rakuten · `tcb` = TopCashback (기본 캐시백 %)
- `rkUpTo`/`tcbUpTo` = 그 값이 "최대 N%" 라는 뜻 (확정치가 아니다)
- `rkFlat` = % 가 아니라 $ 고정 (Amazon 류)
- `rkFail`/`tcbFail` = **못 읽었다.** ⚠️ 값은 `null` 이고 **0 이 아니다** —
  0 으로 적으면 나중에 "그 시각에 0으로 떨어졌다"는 **없는 변동**을 만들어낸다
- 그 회차에 아예 줄이 없는 판매처 = 연속 실패로 **건너뛴** 것 (차단 회피)

## 종료

`scripts/probe-rates.mjs` 가 시작일 +5일이 지나면 스스로 아무것도 안 하고 끝난다.
워크플로를 지우는 걸 누가 잊어도 요청이 계속 나가지 않는다.

## 중간 관측 (2026-08-25 12:57Z ~ 23:34Z · 13회차)

### 요율 변동 — 사실상 없다

8곳 중 7곳이 11시간 동안 **완전히 고정**이었다.

```
booking ≤8%/0%   expedia ≤3%/≤10%   gnc 2%/8%    macys 4%/≤7%
nike    4%/6%    logitech 3%/4%     athleta 2%/4%
```

**adidas 하나만 움직였고, 그것도 애매하다:**

```
12:57Z ~ 21:39Z   rk ≤4% (upTo)        ← 11회차 고정
22:41Z            rk  4% (upTo 사라짐, 숫자는 그대로)
23:34Z            rk  FAIL
```

⚠️ **"요율이 바뀌었다"로 읽지 말 것.** 바뀐 건 숫자가 아니라 **"최대"라는 말**이다
(Rakuten 타이틀에서 `Up to` 가 빠졌다). 두 가지로 읽힌다:

- **진짜 변경** — "최대 4%" → "4% 확정". 그렇다면 의미 있다(≤4% 와 4% 는 사용자에게 다른 값)
- **페이지 쪽 사정** — 타이틀 형식이 바뀌었거나 다른 변형이 나왔다

**이 데이터로는 둘을 구분할 수 없다.** 그리고 **바로 다음 회차에 그 판매처만 FAIL** 했다 —
값이 바뀐 게 아니라 adidas 페이지에 뭔가 일어나는 중일 가능성이 더 커 보인다.
한 판매처 · 연속 두 회차 · 관측 구간 끝이라 **판정을 미룬다.**

### 차단 징후 — 없다

실패 1건 / 104줄 · 건너뜀 0회 · 13회차 전부 8줄씩 온전 · 응답 형태 변화 없음.

### ⚠️ cron 의 분(minute)은 지켜지지 않는다

`cron: '7 * * * *'` 인데 실제 실행 시각:

```
14:00 · 15:00 · 15:55 · 16:51 · 17:42 · 18:54 · 19:42 · 20:42 · 21:39 · 22:41 · 23:34
간격:   60 · 56 · 56 · 50 · 72 · 48 · 60 · 57 · 62 · 53분
```

**분은 아무 의미가 없고** 간격도 48~72분으로 흔들린다. 시간당 1회는 지켜지므로
측정에는 지장이 없다.

⚠️ **`update-rates.yml` 의 `:17` 도 같은 처지다.** 그 값은 *"정각 혼잡 회피"* 를 근거로
골랐는데 **그 근거가 성립하지 않는다.** 지금 판단에 영향은 없다(P3 가 재는 건
*포털이 언제 바꾸나*지 *우리가 언제 재나*가 아니다). 나중에 갱신 지연이 문제 되면
여기서 시작할 것.

### 잠정 판단 (결론 아님)

11시간 · 8곳에서 변동이 사실상 0이다. 이게 유지되면 *"update-rates 를 몇 시에 돌리나"* 는
**애초에 별로 중요하지 않은 질문**이었다는 뜻이 된다.

⚠️ **다만 11시간은 하루도 안 된다.** 대상 선정 근거였던 변동률(.36~.88)은 **일 단위**다.
하루 한 번 바뀌는 값이면 지금 창에 안 걸리는 게 정상이다. 창은 8/30 까지다.

## adidas 판정 (2026-08-26 01:55Z 회차까지 · 14회차)

**어제 "판정 미룸"으로 뒀던 건. 이제 판단할 근거가 생겼다.**

```
12:57Z ~ 21:39Z   rk ≤4%  (upTo)   ← 11회차
22:41Z            rk  4%  (upTo 사라짐)
23:34Z            rk  FAIL
01:55Z            rk  4%  (upTo 여전히 없음)   ← ★ 복구 후에도 유지
```

⭐ **결정적인 건 마지막 줄이다.** 실패를 한 번 거쳐 복구된 뒤에도 `upTo` 가 돌아오지
않았다. 일시적인 페이지 변형이나 A/B 였다면 **되돌아왔을 가능성이 높다.** 안 돌아왔다.

→ **Rakuten 이 adidas 를 "최대 4%" 에서 "4% 확정" 으로 바꾼 것으로 본다.**

⚠️ 다만 확정은 아니다: 변경 후 성공 관측이 **2회뿐**이고, 그 사이에 실패가 한 번 끼어
있어서 "adidas 페이지가 손보는 중" 이라는 설명도 완전히 배제되지 않는다.
다음 회차들에서 `4%` 가 계속 유지되면 그때 확정으로 본다.

⭐ **이게 P3 가 지금까지 잡은 유일한 변동이고, 숫자가 아니라 `upTo` 플래그가 바뀐 것**이다.
`upTo` 를 버리지 않고 계속 실어 나른 설계가 없었으면 **이 변동은 보이지도 않았다**
(4% → 4% 로 보였을 것이다).

## ⚠️ 측정 구멍 — GitHub 이 회차를 통째로 건너뛴다

```
23:34:31Z  회차 있음
   ← 2시간 21분 동안 없음
01:55:38Z  회차 있음
```

Actions 실행 이력에도 **그 사이에 실행 자체가 없다**(실패가 아니라 미실행).
GitHub 의 예약 실행은 best-effort 라 부하가 걸리면 **건너뛴다.**

⚠️ **우리 가드로는 이걸 못 잡는다.** 워크플로의 "창이 열렸는데 안 쌓였으면 실패" 는
**실행이 됐을 때만** 작동한다. 아예 안 도는 회차는 아무 흔적을 안 남긴다.
→ 분석할 때 **회차 간격이 90분을 넘는 구간**을 구멍으로 표시하고 읽을 것.
   "그 시각엔 변동이 없었다" 로 읽으면 안 된다 — **안 쟀다.**

지금까지의 간격: 48~72분이 정상 범위, 그리고 위 141분 구멍 1개.

# 최종 결과 (2026-08-25 12:57Z ~ 2026-08-29 21:41Z · 37회차 · 296줄)

측정 창이 스스로 닫혔다. Actions 로그에 그대로 남아 있다:
`측정 창(2026-08-25 +5일)이 끝났다 — 아무것도 하지 않고 종료.` →
`측정 창 종료 — 정상적으로 아무것도 안 썼다`
(창이 끝나서 안 쓴 것과 고장나서 못 쓴 것을 가르는 `window=open|closed` 가드가 제대로 작동했다.)

## ⛔ 원래 질문에는 **답하지 못했다**

P3 가 재려던 건 **"하루 중 언제 요율이 바뀌는가"** 였다. **못 잰다.**

**90분을 넘는 구멍이 16개**고, 그중 다수가 **5~13시간**짜리다:

```
08-26T23:26 → 08-27T09:36   609분
08-27T09:36 → 08-27T20:22   646분
08-28T05:20 → 08-28T18:36   796분
08-29T02:07 → 08-29T09:59   471분
```

첫날은 48~72분 간격으로 잘 돌다가 **08-26 오후부터 무너졌다.** GitHub 예약 실행이
best-effort 라 계속 건너뛴 것이다(실패가 아니라 미실행 — Actions 이력에 실행 자체가 없다).

**변동이 10시간짜리 구멍 안에서 일어나면 시각을 특정할 수 없다.** 그래서
*"몇 시에 바뀌는가"* 는 이 데이터로 답할 수 없다. **표본이 부족한 게 아니라 표본이 없다.**

⚠️ 교훈: **GitHub Actions cron 은 시각을 재는 측정에 못 쓴다.** 분이 안 지켜지는 정도가
아니라 **회차를 통째로 건너뛴다.** 시각 측정이 필요하면 상시 켜진 곳에서 돌려야 한다.

## ✅ 대신 알게 된 것 — 그리고 이게 초기 판단을 뒤집는다

**8곳 중 6곳이 5일 안에 바뀌었다.**

```
booking    ≤8% → ≤6%(08-27) → ≤5%(08-28) → ≤4%(08-29)      계속 내려갔다
expedia    ≤3% → ≤6%(08-26) → ≤3%(08-28) · tcb ≤10% → ≤7%
adidas     ≤4% → 4%(08-25) → ≤8%(08-26) · tcb ≤5% → ≤8% → ≤9%
logitech   3% → 9% (08-28)                                   3배로 뛰었다
athleta    2% → 4% (08-27)
macys      값 변동 없음(FAIL 1회뿐)
gnc·nike   변동 없음
```

⚠️ **첫 11시간 보고의 잠정 판단은 틀렸다.** 그때 *"변동이 사실상 0이니 update-rates 를
몇 시에 돌리느냐는 별로 중요하지 않은 질문이었을 수 있다"* 고 적었다. **5일로 보면
요율은 자주 바뀐다** — 다만 **시간 단위가 아니라 일 단위**로 바뀐다.
11시간 창에서 안 보인 건 변동이 없어서가 아니라 **창이 짧아서**였다.
대상 선정 근거였던 일 단위 변동률(.36~.88)이 오히려 맞았다.

⚠️ **adidas 판정도 정정한다.** 08-26 시점에 *"Rakuten 이 최대 4% → 4% 확정으로 바꿨다"* 고
적었는데, **그 상태는 약 15시간만 유지되고 다시 `≤8%` 로 갔다.** 실제 변경이었던 건
맞지만 **정착한 새 상태가 아니라 움직이는 중의 한 단계**였다. 관측 2회로 "판정"한 게
성급했다.

## 그래서 실무적으로

- **매일 1회 갱신은 타당하다** — 일 단위로 바뀌니까
- **몇 시에 돌릴지는 여전히 근거가 없다.** `update-rates.yml` 의 `:17` 은 *"정각 혼잡 회피"*
  가 근거였는데 **그 근거도 성립하지 않는다**(분이 안 지켜진다). 근거 없는 값으로 남는다
- ⭐ **`upTo` 플래그가 값만큼 자주 바뀐다.** adidas 는 값이 아니라 플래그가 먼저 움직였다.
  `upTo` 를 버렸다면 이 변동은 보이지도 않았다

## 이 워크플로는 이제 지워도 된다

스크립트가 스스로 아무것도 안 하므로 **켜 둬도 해는 없다.** 다만 매시간 빈 실행이 돈다.
`.github/workflows/probe-rates.yml` 삭제 = main 커밋 1회 = 배포 1회.
